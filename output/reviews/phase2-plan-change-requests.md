## P2-CR-01: 적5와 일반5의 기본 동등성 통일

### 요청 의도

사용자는 같은 무늬의 적5와 일반5를 `==` 비교에서도 같은 수패로 취급하는 것이 맞다고 제안했다. 적5의 그림과 보너스 정보는 보존하면서, 기본 비교는 패 종류를 기준으로 통일한다.

예를 들어 적5만과 일반5만은 같고, 5만과 5통은 다르다. 이 요청은 적도라 점수나 적5 속성을 제거하자는 뜻이 아니다.

### 기존 계획과 그 근거

- [02-CONTEXT.md D-06](../../.planning/phases/02-shared-rules-core/02-CONTEXT.md)은 값의 정체성을 `패 종류 + 적5 여부`로 정하고, `==`·`Equals`·`GetHashCode`에 같은 기준을 적용한다. 화료 분해와 대기 계산은 별도로 적색을 무시한다.
- [02-01-PLAN.md](../../.planning/phases/02-shared-rules-core/02-01-PLAN.md)는 이를 `(TileID, isAkaDora)` 기반 operator·typed/object Equals·hash·CompareTo 구현으로 구체화한다.
- [02-RESEARCH.md](../../.planning/phases/02-shared-rules-core/02-RESEARCH.md)는 적5와 일반5의 값 비교 결과가 달라지면 기존 `==` 기반 몸통 판정이 깨질 수 있다고 설명하고, solver의 종류 비교를 분리하도록 요구한다.
- 당시 논의에서 사용자가 선택한 것은 실물 패마다 고유 ID를 만들지 않고 패 종류와 적5 속성을 보존하는 방향이었다. 당시 설명은 몸통·대기 판정에는 종류를, 표시·점수 및 시드 재현에는 종류와 적5를 함께 사용한다는 내용이었다. `적5 == 일반5`를 `false`로 변경하는 선택은 별도로 명확히 설명되지 않았다.

적5의 표시·점수 차이를 보존하려는 기존 설계의 목적은 타당하다. 다만 적5 속성을 보존하는 것과 기본 동등성에 그 속성을 포함하는 것은 별개의 결정이다. 기존 문서의 “이미 확정된 계약”이라는 표현은 이 구분을 반영하여 수정할 필요가 있다.

연구 문서가 인용한 [Microsoft 동등성 지침](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/expressions/equality)은 비교 API 사이의 일관성을 뒷받침한다. 적5 속성을 동등성 기준에 반드시 포함해야 한다는 근거는 아니다.

### 제안하는 계약

| 용도 | 제안 기준 |
|---|---|
| `==`, `!=`, `IEquatable<MahjongTile>.Equals`, `Equals(object)` | `TileID`만 비교 |
| `GetHashCode` | 동등성에 맞춰 `TileID`만 사용 |
| 기본 `CompareTo` | `TileID` 기준으로 정렬하며 같은 종류의 적5·일반5는 0 반환 |
| 머리·몸통·화료 분해·대기 계산 | 적5와 일반5를 같은 종류로 계산 |
| 적도라 점수·패 그림·공개 도라 표시 | 원본 패의 `isAkaDora` 속성을 보존하여 사용 |
| 패산 순서·셔플 재현 등 적색까지 같아야 하는 검증 | `(TileID, isAkaDora)`를 명시적으로 비교 |
| 선택한 손패의 타패·제거 | 선택 인덱스로 해당 항목을 조작 |

`isDora`·`doraCount` 등 국에 따라 달라지는 계산 결과는 기본 동등성에 포함하지 않는다. 기존 표시패 resolver 방향을 유지한다. 실제 표시 정렬에 적색 우선순위가 필요하다면 해당 표시 경계의 정렬 기준으로 명시하며, 기본 동등성 변경과 묶어 새 정렬 기능을 추가하지 않는다.

### 현재 코드에 더 적합하다고 판단한 이유

[MahjongTileAndBlock.cs](../../Assets/Scripts/AL-1S/MahjongTileAndBlock.cs)의 현재 `==`와 `CompareTo`는 이미 `TileID`만 사용한다. [MahjongUtilities.cs](../../Assets/Scripts/AL-1S/MahjongUtilities.cs)의 머리·커쯔 판정도 이 의미를 사용한다. 반면 `Equals(object)`는 `base.Equals`에 위임하여 적5·도라 상태를 포함한 필드를 비교한다.

따라서 교정 대상은 비교 API 사이의 의미 불일치다. `==`가 적5와 일반5를 같은 종류로 취급하는 동작 자체를 결함으로 기록하지 않는다. 서로 다른 값이 같은 해시를 갖는 것만으로 해시 계약 위반이라고 설명해서도 안 된다.

기존 종류 비교 의미를 유지하면서 `Equals`를 맞추면, 일반적인 규칙 계산을 위해 별도 종류 비교 API를 반복 도입할 필요를 줄일 수 있다. exhaustive decomposition을 위한 34종 count-vector는 그대로 유효하며, 이 요청 때문에 solver 알고리즘을 변경하지 않는다.

### 함께 점검해야 할 영향

1. **인덱스로 선택한 패의 제거:** [MahjongRound.cs](../../Assets/Scripts/AL-1S/MahjongRound.cs)의 리치 후보 계산에는 `tenpaiCheckHand.Remove(fullHand[i])`가 있다. 종류 기준 Equals에서는 선택한 일반5 대신 앞에 있는 적5가 제거될 수 있으므로, 이처럼 원래 위치를 아는 경로는 `RemoveAt(i)` 등 인덱스 조작으로 계획한다. 실제 타패 경로는 이미 선택 인덱스를 전달한다.
2. **컬렉션 연산:** `Remove`, `Contains`, `IndexOf`, `Distinct`, `GroupBy`, `HashSet`, `Dictionary` 호출에서 종류 비교와 적색까지 포함한 비교 중 어느 것이 필요한지 확인한다. 기본 종류 비교가 의도에 맞으면 그대로 사용한다.
3. **적색 정보 보존:** 종류 기준으로 묶은 solver 데이터와 별도로 원본 손패·화료패·선언된 몸통의 적5 정보가 점수 및 표시까지 보존되게 한다. 집합으로 중복을 제거한 패 목록을 실제 손패로 사용하지 않는다.
4. **시드·패산 검증:** 기본 Equals에 의존한 `SequenceEqual`만으로는 적5와 일반5의 위치가 바뀐 패산을 구분할 수 없다. 적색을 포함하는 명시적 비교를 사용한다.

`List<T>.Remove`가 기본 동등성 비교로 첫 일치 항목을 제거하는 동작은 [Microsoft 문서](https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.list-1.remove?view=net-9.0)에 따른다.

### 계획에 반영할 검증 조건

- 같은 무늬의 적5·일반5는 `==` 및 typed/object `Equals`가 참이고 `!=`는 거짓이다. 해시는 같으며 기본 `CompareTo`는 0이다. 서로 다른 패 종류는 같지 않다.
- default/invalid 값도 동등성 법칙을 유지하며, 적5·일반도라 상태 차이가 기본 동등성에 영향을 주지 않는다.
- 적5가 섞인 머리·커쯔·순쯔·치또이츠 및 대기 계산이 정상적으로 처리된다.
- 일반5를 인덱스로 제거하면 적5가 남고, 적5를 인덱스로 제거하면 일반5가 남는다. 실제 타패와 리치 후보 계산 등 해당 경로에서 적색 정보가 보존된다.
- 적도라 판수와 패 그림·표시는 원본 적5 속성을 반영한다. 종류 비교를 통일했다는 이유로 적도라 보너스가 사라지지 않는다.
- 패산은 여전히 136장, 종류별 4장, 무늬별 적5 1장이다. 시드 재현 검증은 적색 위치까지 확인하고, 적5와 일반5 위치만 교환한 잘못된 순서를 구분한다.
- 기존 Phase 1 회귀와 Phase 2의 RED/GREEN 증거 요구를 유지한다. 현재 `적5 == 일반5`가 참인 동작은 RED 결함으로 삼지 않고, 실제 `==`/`Equals` 불일치를 회귀 대상으로 삼는다.

위 항목은 이후 계획 수정 및 구현에서 사용할 검증 조건이다. 이 제안 문서 작성 과정에서 코드 변경이나 Unity 테스트를 수행했다는 의미가 아니다.

## P2-CR-02: 솔로 지급 오류의 검증 시점과 수정 담당 플랜 정렬

### 요청 의도

### 현재 계획과 코드에서 확인한 불일치

- [02-04-PLAN.md Task 2](../../.planning/phases/02-shared-rules-core/02-04-PLAN.md)는 실제 솔로 쯔모가 론 금액을 사용하는 결함을 production public score path에서 RED로 고정하고, 같은 사례가 GREEN에서 올바른 쯔모 총액을 반환하도록 요구한다.
- 그러나 해당 task의 수정 대상은 회귀·적합성 테스트와 `MahjongWinInfo.cs`, `MahjongUtilities.cs`다. 실제 지급 경로인 `MahjongRound.cs`는 읽기 대상일 뿐 수정 대상이 아니다.
- [MahjongRound.HandlePlayerWin](../../Assets/Scripts/AL-1S/MahjongRound.cs)은 현재 친이면 `scoreTable.oyaRon`, 비친이면 `scoreTable.zaRon`을 선택해 `ModifyPlayerToScore`에 전달한다. 계산 코어가 쯔모 금액을 정확히 반환하더라도 이 호출부가 론 필드를 계속 읽으면 실제 지급 오류는 남는다.
- 이 호출부와 솔로 매니저를 `MahjongPaymentResult.WinnerIncome`에 연결하는 작업은 [02-05-PLAN.md Task 1](../../.planning/phases/02-shared-rules-core/02-05-PLAN.md)에 배정되어 있다. 따라서 현재 범위대로라면 `02-04`에서 실제 솔로 지급 경로까지 GREEN이라고 완료 선언할 수 없다.

### 제안하는 역할 배분

- `02-VALIDATION.md`, `02-RESEARCH.md`, `02-08-PLAN.md` 및 관련 증거 매핑: 해당 결함의 담당 플랜과 RED/GREEN 수집 시점을 일치시킨다. 테스트 이름·개수·실행 필터를 조정한다면 연결된 검증 명령과 기대 개수도 함께 갱신하며, 최종 회귀 커버리지를 줄이지 않는다.

### 계획에 반영할 검증 조건

- 회귀 입력은 선택한 룰에서 유효한 화료이며, **론 금액과 쯔모 지불 합계가 실제로 다른 사례**여야 한다. 현재 `PLAYER-OBS-01`의 6판 20부 비친 사례는 두 총액이 모두 12000이므로, 이 사례만으로 론 필드 오사용을 검출했다고 판단하지 않는다. 기존 관찰 사례는 유지하고 별도의 결함 검출 사례를 사용한다.
- 계산표의 값만 검사하지 않고 실제 솔로 화료 경로가 플레이어 점수와 거리 서비스에 전달하는 금액 및 전달 횟수를 검사한다. `02-05`의 연결 수정 전에는 잘못된 지급 금액 때문에 assertion이 실패하고, 수정 후에는 동일 입력·동일 기대값으로 통과해야 한다.
- `02-04`는 자신의 계산 검증과 그 시점의 기존 회귀를 통과해야 한다. `02-05`는 추가한 실제 지급 회귀까지 통과해야 하며, 컴파일 오류나 테스트 미발견을 RED 증거로 사용하지 않는다.
- RED/GREEN은 각각 실제 XML·테스트 이름·양수 실행 개수·커밋으로 추적한다. GREEN은 기존 gate의 zero non-passed 조건을 유지하며, 자동 검증을 Player GUI 관찰 완료로 대체하지 않는다.

이 항목은 검증 책임 배분의 수정 제안이다. 현재 Phase 2 계획·코드에 반영하거나 Unity 테스트를 실행한 결과가 아니다.
